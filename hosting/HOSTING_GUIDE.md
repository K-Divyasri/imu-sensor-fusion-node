# Hosting & deploying this project (all free)

Two things, neither costing anything — and one thing this project
**deliberately doesn't try to host**, explained below.

## Why there's no live cloud dashboard for this project

Project 13's climate monitor reports over MQTT to a cloud broker, so a
hosted Streamlit app can subscribe to it live from anywhere on the
internet. This project's device talks over a **wired USB serial
connection** straight to whatever computer it's plugged into — there's no
broker, no network hop, nothing a hosted web app could reach into. A
"live" dashboard claiming to show real-time data from a device plugged
into someone else's laptop would just be lying. Instead, this project
hosts a **replay/analysis dashboard** — real, honest, and still useful:
upload a recorded session (or generate a synthetic one on the spot) and
see the same charts a live version would have shown.

## Part 1 — put your code on GitHub

From the project root (`16-imu-sensor-fusion-node`):

```powershell
git init
git add .
git commit -m "IMU Sensor-Fusion Node"
git remote add origin https://github.com/YOURNAME/imu-sensor-fusion-node.git
git branch -M main
git push -u origin main
```

Confirm `build_from_scratch/firmware/imu_node/.gitignore` and
`build_from_scratch/host/.gitignore` did their jobs — `.pio/`, `build/`,
and stray `*.csv`/`*.bin` files shouldn't appear in the repo.

---

## Part 2 — the CI gate (GitHub Actions)

Copy `github_actions/ci.yml` into `.github/workflows/ci.yml`. It runs
three independent, keyless checks on every push — no hardware, no serial
port, no Windows machine needed on the runner:

- **Firmware compile check** (`pio run`) — proves the ESP32 firmware
  still compiles.
- **C++ host app build + test** (`cmake` + `ctest`) — GitHub's own
  `ubuntu-latest` runners ship g++ and CMake already installed, so unlike
  this project's own local verification, **no Docker is needed in CI** —
  it just builds and runs `imu_host_tests` directly.
- **Python test suite** (`pytest` against `imu_sim`) — the wire codec and
  fusion math, the same tests this project was built and verified
  against.

None of these three jobs touch a real serial port or a real board —
that's the one thing that has to stay a manual, on-your-own-bench step
(see `knowledge/09_wiring_and_bring_up.md`).

## Part 3 — host the replay dashboard (Streamlit Community Cloud)

1. Push your repo to GitHub (Part 1) if you haven't.
2. Go to [share.streamlit.io](https://share.streamlit.io), sign in with
   GitHub, click **New app**.
3. Point it at your repo, branch `main`, app file
   `build_from_scratch/webapp/dashboard_app.py`.
4. No secrets needed — the app only reads an uploaded CSV or generates
   synthetic data via `imu_sim`, nothing external at all.
5. Make sure Streamlit Cloud can find the requirements — copy
   `build_from_scratch/webapp/requirements.txt`'s contents to a
   root-level `requirements.txt`, or point Streamlit Cloud's advanced
   settings at the real path.
6. Deploy. Click **Generate synthetic session** on the live app to
   confirm it works with zero setup, then try uploading a real
   `--csv-out` file from your own bench session.
7. Put the live dashboard URL at the top of your repo README.

## What to actually show in an interview

- The **live dashboard**, with a real recorded session uploaded — not the
  synthetic generator, which anyone could click. A real CSV, generated by
  the real compiled C++ host app reading a real board over USB, is the
  actual proof.
- The **green Actions badge**, and being able to explain exactly what its
  three jobs do and don't prove (compiles + unit-tests cleanly on a clean
  machine; does NOT prove the live serial path works — that's the one
  thing you verified by hand, which is worth saying out loud, not
  hiding).
- A short **video of the real bench setup**: the board being tilted by
  hand, the host app's terminal output (or the dashboard, fed a session
  recorded moments earlier) tracking it live.

See `deploy_checklist.md` before you share any of these.
